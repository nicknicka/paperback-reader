# 分页性能记录

## 外部参考结论

- Readium CSS 使用 CSS multi-column 做分页，因为它跨平台、响应式、经过大量阅读系统验证；阅读系统负责控制列宽、列数、间距和正文宽度。
- epub.js / react-reader 的分页模式也依赖 iframe + CSS columns，章节级渲染，翻页时移动当前章节的分页视图。
- fread-ink/ebook-paginator 关注 WebKit 上的分页性能和低内存，核心观点是：不要为了显示第一页而强制同步分页整个大文档；异步/分步分页能减少首屏阻塞。

## 当前基准

环境：Vite dev server + 浏览器 DOM 测量容器。测试文本为中文段落，页面宽度 680px，高度 650px，字号 19px，行距 1.88。

优化前：

| 段落数 | 页数 | 耗时 |
| --- | ---: | ---: |
| 200 | 50 | 15ms |
| 1000 | 247 | 48ms |
| 3000 | 741 | 118ms |
| 10000 | 2469 | 373ms |

优化后：

| 段落数 | 页数 | 耗时 |
| --- | ---: | ---: |
| 200 | 50 | 11ms |
| 1000 | 247 | 46ms |
| 3000 | 741 | 114ms |
| 10000 | 2469 | 359ms |

函数级优化收益有限，但页数保持一致，说明行为没有偏移。更重要的体验优化已经放到阅读器层：分页缓存、下一帧调度、相邻章节空闲预分页。

## 已做优化

- 分页函数从“每次重画当前页所有段落”改为“增量追加测量”，减少 DOM 重建。
- 阅读器按 `book + chapter + viewport + settings` 缓存分页结果，返回已分页章节时不重复计算。
- 章节分页放到 `requestAnimationFrame`，让界面先响应，再执行计算。
- 当前章节分页完成后，在空闲时间预分页相邻章节，降低连续翻章节时的等待。

## 后续可选方案

- CSS columns 模式：更贴近 Readium/epub.js 的成熟做法，翻页性能好，但长章节整体布局仍可能卡顿，且页级内容不可直接作为数组管理。
- 分步分页：每次只算前后若干页，首屏更快，但总页数和跳转目录需要处理“未知页数”状态。
- Worker 粗估 + DOM 精修：Worker 先按字符宽度估算页边界，主线程只校验边界页，复杂度更高，适合后续长篇性能专项。
